# Operational leakage assurance

The default `/rebate-protection` view is now Leakage controls. Earlier contract checks, rebate scenarios, and blind detection-only challenges retain their routes. `oas_` work-detail routes show the new agent history. The existing `rebate-protection` registry ID now represents Operational leakage protection; no new operational agent or queue is created.

## What executes

The demo creates an isolated book covering eight areas: contract mapping, drug definitions, adjudication, guarantee changes, rate events, client invoices, manufacturer invoices/collections, and nonstandard notice obligations. Each named control has corrupted, clean and missing/conflicting-source examples. IDs are opaque; the answer, seed and fault identities are withheld until the initial execution has frozen its outputs. All terms, event rules and source records are synthetic, including Tennessee. This does not parse or certify an actual executed contract.

Contract/reference records carry clause, version, effective dates, recorded time, population and approval. Implementations carry separate actual values. Financial controls derive obligations from source quantities, rates, fees, credits, adjustments and dependencies. Drug classifications are separately represented. Adjudication checks call Glass's actual `adjudicate` function in isolated contexts; a separately authored golden fixture defines results. Reversal testing includes the sandbox reversal-ledger invariant rather than claiming to exercise the operational reversal API.

The detector has no fixture or answer-key import. Repair receives only working records and findings. The separate verifier compares frozen initial findings and final records with expected results and checks clean-record regressions. It does not call detector, repair or adjudication. Same-application separation is not third-party audit independence.

## Corrections

Run checks & safe fixes prepares patches and automatically regenerates the deterministic manufacturer draft. Changes to contracts, classification, access, claim financial results or client invoices require simulated approval. Shared benefit configuration blocks downstream claims, which in turn block a dependent client invoice. Once the root is corrected, checks run again and newly actionable patches appear. Rejected patches remain unresolved.

Each repair has before/after values, guard checks against stale requirements and records, actor, wall-clock time and synthetic evidence cutoff. It can only become Verified after the changed working record passes a retest. Independent verification remains a separate proof result. Cycles, ambiguous authority and absent source manifests remain Not verified.

Approval of an external-facing correction only prepares a draft. A separate, explicitly simulated acceptance, delivery or settlement action provides sandbox evidence. Corrected manufacturer invoices are not cash receipts. An expired notice deadline stays breached. Late fulfillment is not presented as removing the original breach. Contractual top-up expense persists when valid guarantees exceed manufacturer economics.

## Persistence and boundaries

AssuranceRun stores the immutable baseline, current working book, initial and current findings, patches, append-only audit history, version identifiers, independent score, private answer commitment and input hash. This table has no operational foreign keys; no Claim, AgentRun, AgentProposal, invoice, benefit release or payment record is modified.

The API at `/api/operational-assurance` supports create, run, simulated review and simulated external evidence plus read/export. Existing authentication, demo gate and same-origin mutation checks apply. Sponsor/tenant scope and cutoff apply to every read and update. Creation keys, guarded revisions and recorded decisions protect retries. A Postgres transaction/advisory lock serializes mutations and atomically records all effects. Failed transactions leave no partially applied repair or recorded approval.

Synthetic evidence time and real recording time are labeled separately. Moving the selected clock before the book cutoff hides that book. Source versions and transactions after the book cutoff cannot drive checks. This is a frozen demonstration, not continuous monitoring.

## Interpretation

Detection, initially blocked/missed records, false alarms, exact quantified discrepancies, verified repairs, remaining faults, unknown evidence and clean-record regressions are separate metrics. Downstream issues initially blocked by configuration count as initially missed/blocked rather than inflating detection. Missing terms remain unknown even when the scenario author knows the intended answer.

Financial discrepancies are record-level differences, not additive savings. Root/transaction/invoice controls can overlap, and valid employer entitlements must not be described as avoidable losses. Simulated collection evidence does not prove actual savings. No real money movement, external submission or notification occurs. Results support a defined synthetic demonstration, never a claim of universal zero leakage or actual Caremark savings.

Verification includes independently authored engine outcomes, all-area controls, approval/rejection and stale-change checks, combined dependencies, partial collection timing, guarantee shortfalls, source omissions, future suppression, idempotency, access/isolation tests, local UI/mobile checks and deployed playback for both sponsor contexts.
